# Day-5 Frontend Data Contract

Generated by `scripts/build_frontend_data.py`; tested by
`tests/test_build_frontend_data.py` (25 tests).

```
python scripts/build_frontend_data.py --out frontend/public/data
```

The generator is a READ → SELECT → RESHAPE → WRITE adapter. It contains no
analytical logic. Every value below is either **copied verbatim** from a
Day-1..Day-4 artifact or is a **DERIVED** field — a count, a dict lookup,
or a key lifted out of a mapping — and every derived field is marked as
such here. If a number is wrong on screen, it is wrong in the source
artifact; the bridge does not compute anything that could diverge.

## Session

**Source:** `reports/day4/instrumentation_health_dataset_{a,b}.json`
**Generated by:** `scripts/analyze_instrumentation_health.py`
**Transformation:** union of the two health files, joined with execution
counts; sorted by `(dataset, session_id)`.

| Field | Required | Origin |
|---|---|---|
| `session_id` | yes | verbatim |
| `n_events` | yes | verbatim |
| `n_events_with_browser_domain` | yes | verbatim |
| `browser_domain_coverage` | yes | verbatim |
| `n_distinct_browser_domains` | yes | verbatim |
| `status` (`healthy`/`degraded`) | yes | verbatim |
| `warnings` | yes | verbatim |
| `dataset` | yes | **DERIVED** — which health artifact the row came from |
| `operator` | yes | **DERIVED** — machine segment parsed from `session_id`; tested to agree with the `operator` field on Dataset-B execution records |
| `n_executions` | optional | **DERIVED** — counted from the execution artifact. **`null` for Dataset A**, which has no persisted executions — deliberately not `0`, which would read as "zero work happened" |

## HR/Payroll evidence

**Source:** `reports/day3/hr_payroll_dominant_path_dataset_b.json` +
the DFG/similarity blocks from the mining results.

`variant_split` is carried **explicitly at the top level** as well as
inside `dominant_path`:

```json
{"dominant":    {"n": 94, "share": 0.7705},
 "word_detour": {"n": 24, "share": 0.1967},
 "rare_edge":   {"n":  4, "share": 0.0328}}
```

This matters: the 94 / 24 / 4 split is **not derivable from
`variants.json`**, which holds 7 generic HR variants keyed by signature.
Without carrying it across, the Process Explorer would have to re-derive
the dominant/detour/rare classification in JavaScript — a fork of Day-3
forensic logic.

## NOT AVAILABLE

Stated explicitly so the frontend never fabricates them:

1. **Raw per-event streams.** `dataset_a/` and `dataset_b/` are gitignored
   (~2.8 GB, includes screenshots) and will not exist on a fresh clone. The
   finest persisted granularity is `ordered_steps`.
2. **Dataset-A predicted execution boundaries.** The locked pipeline is
   evaluated but never serialises its predictions — only pooled and
   per-session metrics exist. Producing them would mean adding an export
   path through the locked segmentation architecture.
3. **Directly-follows graphs for the 20 non-HR processes.** Computed
   in-memory by `analyze_problem2_process_mining.py` and discarded; only
   `hr_payroll_dfg` is persisted.
4. **Trace-similarity evidence for non-HR processes.** Same reason.
5. **Narrative reasoning.** The engineering rationale lives in `.md` prose
   across `reports/day1..day4/`, not in any JSON.

## Day-6 additions

Two passthroughs were added for the Automation Decision Center. Both copy
fields **verbatim** from canonical artifacts the bridge already reads or from
a Day-4 artifact; neither changes any analytical meaning, and no value is
recomputed.

### 1. `opportunities.json` → `sensitivity_scenarios`

**Source:** `reports/day3/problem2_audit_results.json::sensitivity_analysis`
**Generated by:** `scripts/audit_problem2_process_mining.py`
**Transformation:** none — copied verbatim.

Per-scenario detail for the 8 weighting scenarios, each with `hr_rank`,
`top5`, `spearman_vs_default`, `top_candidate_changed`. Previously only the
aggregate `sensitivity_summary` was exposed, which could say *"#1 in 5 of 8"*
but not **which** assumptions move the ranking.

Scenario names are shown exactly as the artifact records them and are never
renamed. Note the field is named `hr_rank`: the artifact tracks this
specifically for the HR/Payroll candidate, so the Decision Center shows the
scenario table only for that process rather than reinterpreting it for others.

**Worst HR rank across all 8 scenarios is 3** (`manual_effort_heavy`,
`volume_deemphasized`, `correlation_aware`), consistent with
`final_ranking_robustness_table[0].worst_rank = 3`.

### 2. `instrumentation-sensitivity.json` (new file)

**Source:** `reports/day4/instrumentation_sensitivity_check.json`
**Generated by:** `scripts/run_instrumentation_sensitivity_check.py`
**Transformation:** none — selected top-level fields copied verbatim.

The Day-4 Case A / Case B comparison: 645 → 571 executions after excluding
the 2 instrumentation-degraded Dataset-B sessions, with the full 21-row
`ranking_comparison`.

**Value discipline:** `0.4401` remains the canonical HR Opportunity
everywhere. `0.4180` appears **only** as `opportunity_b` — the Day-4
degraded-excluded sensitivity case — and is never presented as the headline
figure. Four tests guard this.
